## 확정한 원인 경로와 미확정 부분

1. **현재 서버 자료와 파서는 정상이다.** 익명 공개 HTTP에서 The미식·진라면·스낵면 모두 PT matched·영양 found를 재확인했다. The미식의 3.1g·0.6g 소수값도 처리됐다. 데스크톱 HTTP 응답은 각각 669ms·248ms였으며 이 값은 당시 Android 통신 시간의 측정값이 아니다.
2. **영양 실패가 유지될 수 있는 캐시 경로는 확인했다.** [ProductLookup.Lookup](../Assets/Scripts/Lookup/ProductLookup.cs)는 영양 예외를 잡고 nutrition=null·detail=영양 조회 확인 불가인 Matched 결과를 반환한다. 같은 파일의 `ProductLookupResult.Cacheable`은 Detail과 무관하게 모든 Matched를 허용한다. [LookupCoordinator.Tick](../Assets/Scripts/Lookup/LookupCoordinator.cs)은 이를 300초 저장하므로 새로 3회 확인해도 같은 부분 실패를 재사용할 수 있다. 기존 컴파일 결과에서도 해당 Matched+실패 detail의 Cacheable=true를 재현했다. 이는 코드 경로의 확정이며 해당 최초 세션의 개별 cache hit를 직접 기록한 로그는 없다.
3. **최초 요청이 왜 실패했는지는 미확정이다.** 기존 릴리스의 catch는 통신·HTTP·시간 초과·파싱 오류의 종류를 남기지 않는다. 원래 예외를 복원할 근거가 없어 시간 초과나 특정 HTTP 상태로 단정하지 않는다. 현재 정상 HTTP·파싱과 새 프로세스 성공은 과거 Android 요청의 정상 동작을 증명하지 않는다.
4. **재실행 후 두 상품 모두 정상 표시를 확인했다.** 기존 PID17303은 중단된 명령 뒤에도 남아 있었으므로 실제 재시작이 안 됐음을 확인하고 PID22159의 새 프로세스를 시작했다. 앱 데이터 초기화 없이 메모리 캐시를 비운 뒤 재시험했다. 영구 저장 자료를 삭제하거나 앱을 다시 설치하지 않았다.
